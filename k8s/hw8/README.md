# Домашнее задание к занятию «Компоненты Kubernetes»

## Цель

Рассчитать ресурсы Kubernetes-кластера для проекта, в состав которого входят:

- отказоустойчивая база данных;
- отказоустойчивая система кеширования;
- frontend;
- backend.

Также необходимо:

1. рассчитать суммарные ресурсы приложений;
2. определить количество worker-нод;
3. учесть отказ как минимум одной worker-ноды;
4. добавить служебные ресурсы Kubernetes и операционной системы;
5. определить итоговое количество нод и их параметры.

# 4. Выбор параметров worker-ноды

Для расчёта выбрана worker-нода следующего размера:

```text
8 vCPU
16 GiB RAM
```

Из физической ёмкости нельзя считать всю память и CPU доступными приложениям.

На каждой worker-ноде резервируется ресурс под:

- операционную систему;
- kubelet;
- container runtime;
- CNI;
- kube-proxy или его замену;
- системные DaemonSet;
- журналирование и фоновые процессы.

Для расчёта принимается следующий резерв:

```text
1 vCPU
2 GiB RAM
```

Тогда условно доступный для прикладных Pod ресурс одной worker-ноды:

```text
CPU:
8 - 1 = 7 CPU

RAM:
16 - 2 = 14 GiB
```

То есть:

```text
Worker physical:
8 vCPU / 16 GiB

Worker allocatable для приложений:
7 CPU / 14 GiB
```

Это проектное допущение для расчёта. В реальном кластере точные значения следует задавать и проверять через `systemReserved`, `kubeReserved`, eviction thresholds и фактический `Node Allocatable`.

# 5. Количество worker-нод без учёта отказа

Проверяем три worker-ноды:

```text
CPU:
3 × 7 = 21 CPU

RAM:
3 × 14 = 42 GiB
```

Требование приложений:

```text
CPU: 17
RAM: 30.25 ГБ
```

Сравнение:

```text
Доступно: 21 CPU / 42 GiB
Требуется: 17 CPU / 30.25 ГБ
```

То есть три worker-ноды способны разместить всю рабочую нагрузку.

Запас при штатной работе трёх worker-нод:

```text
CPU:
21 - 17 = 4 CPU

RAM:
42 - 30.25 = 11.75 GiB
```

Однако такой вариант не удовлетворяет требованию задания о сохранении работоспособности при отказе минимум одной worker-ноды.

```

```

## Состояние после отказа одной worker-ноды

После потери одной ноды остаются три worker:

```text
CPU:
3 × 7 = 21 CPU

RAM:
3 × 14 = 42 GiB
```

Сравниваем с необходимой нагрузкой:

```text
Требуется:
17 CPU
30.25 ГБ RAM

Остаётся после отказа:
21 CPU
42 GiB RAM
```

Запас после отказа одной worker-ноды:

```text
CPU:
21 - 17 = 4 CPU

RAM:
42 - 30.25 = 11.75 GiB
```

Следовательно, схема из четырёх worker-нод удовлетворяет условию N+1.

# 7. Размещение отказоустойчивых компонентов

Самого наличия четырёх worker-нод недостаточно.

Чтобы три реплики БД действительно были отказоустойчивыми, их необходимо распределять по разным worker-нодам.

То же относится к трём репликам кеша.

Для этого в Kubernetes следует применять:

```text
podAntiAffinity
```

или:

```text
topologySpreadConstraints
```

Например, нельзя допустить ситуацию:

```text
worker-1:
  db-1
  db-2
  db-3
```

Так как отказ `worker-1` одновременно уничтожит все три реплики.

Правильный подход:

```text
worker-1: db-1
worker-2: db-2
worker-3: db-3
```

Четвёртая нода обеспечивает запас для rescheduling при отказе одного worker.

Аналогичное распределение необходимо для кеша.

# 8. Control Plane

Worker-ноды не должны быть единственными узлами кластера.

Для production-подобного отказоустойчивого Kubernetes-кластера принимается:

```text
3 control-plane-ноды
```

Используется нечётное количество control-plane / etcd участников, что позволяет сохранить quorum при отказе одной control-plane-ноды.

Для одной control-plane-ноды принимаются параметры:

```text
2 vCPU
4 GiB RAM
40–50 GiB SSD
```

На control-plane работают:

- kube-apiserver;
- kube-controller-manager;
- kube-scheduler;
- etcd;
- системные control-plane компоненты.

Пользовательские приложения на этих нодах в данном расчёте не размещаются.

Всего прикладных Pod:

```text
21
```

При четырёх worker-нодах:

```text
21 / 4 ≈ 5.25 Pod на worker в среднем
```

После отказа одной ноды:

```text

```

Таким образом ограничивающим фактором в данном проекте являются CPU и RAM, а не максимально допустимое количество Pod на ноду.

# 13. Хранилище

В задании не указаны:

- объём базы данных;
- объём данных кеша;
- требования к IOPS;
- размер журналов;
- политика backup;
- срок хранения backup;
- требования к latency.

Поэтому корректно рассчитать объём PersistentVolume по исходным данным невозможно.

В реальном проекте storage для БД следует рассчитывать отдельно с учётом:

```text
рабочий объём данных
+ рост данных
+ WAL / transaction logs
+ snapshots
+ backup policy
+ IOPS
+ latency
+ replication overhead
```

Не следует придумывать размер дисков БД без этих исходных данных.

# 14. Helm

По условию приложение предполагается упаковывать в Helm chart для разных окружений.

В таком chart должны быть параметризованы как минимум:

```text
replicaCount
image.repository
image.tag
resources.requests
resources.limits
storage
service
ingress
affinity / topologySpreadConstraints
```

Разные окружения можно описывать отдельными values-файлами:

```text
values-dev.yaml
values-stage.yaml
values-prod.yaml
```

Например, для production значения `replicaCount` и resources должны соответствовать расчёту из этого задания.

Само задание 3.1 является расчётным, поэтому создание рабочего Helm chart не требуется для доказательства расчёта ресурсов.

# 16. Итог

Для заданной нагрузки выбирается следующий Kubernetes-кластер:

```text
3 × control-plane:
2 vCPU
4 GiB RAM

4 × worker:
8 vCPU
16 GiB RAM
```

Итого:

```text
7 нод
38 vCPU
76 GiB RAM
```

Worker-pool при штатной работе предоставляет приложениям около:

```text
28 CPU
56 GiB RAM
```

После отказа одной worker-ноды остаётся:

```text
21 CPU
42 GiB RAM
```

Это больше требуемых:

```text
17 CPU
30.25 ГБ RAM
```

Следовательно:

- ресурсов для приложения достаточно;
- учтён служебный резерв Kubernetes и ОС;
- кластер выдерживает отказ одной worker-ноды;
- control plane также сделан отказоустойчивым за счёт трёх нод;
- реплики БД и кеша необходимо распределять между worker-нодами через anti-affinity или topology spread;
- storage требует отдельного расчёта, так как исходных данных по объёму и производительности дисков в задании нет.

**Итоговая конфигурация: 3 control-plane + 4 worker = 7 нод.**
